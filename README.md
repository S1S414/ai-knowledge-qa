# 知识库问答系统

> 基于 RAG（检索增强生成）技术的企业文档智能问答系统

---

## 项目背景

企业在日常运营中积累了大量的产品文档、操作手册、FAQ 等文本资料。传统的关键词搜索只能做字符串匹配，无法理解语义——比如搜"怎么退货"找不到"退款流程说明"。

本系统用 **RAG（检索增强生成）** 方案解决这个问题：

1. 把知识库文档拆成小块，用语义模型把每个块转成向量
2. 用户提问时，在向量空间里找最相关的几个块
3. 把相关内容 + 问题一起发给 DeepSeek 生成答案

这样即便是用大白话问，也能命中专业文档里的正确答案。

## 使用方法

### 1. 首次使用
1. 左侧输入 DeepSeek API Key（或确认 `.env` 已配置）
2. 点击「重建索引」按钮
3. 系统自动加载知识库文档并生成语义向量

### 2. 日常使用
- 左侧「知识库文件」点击文件名可预览内容
- 底部输入框输入问题
- 系统检索知识库相关内容 → 调用 DeepSeek 生成回答

### 3. 添加新文档
1. 将 `.txt` 文件放入 `knowledge_base/` 文件夹
2. 点击「重建索引」
3. 新文档即可被检索

## 核心架构（RAG 全流程）

```text
                   离线索引阶段                      在线问答阶段
               ┌─────────────────┐            ┌─────────────────┐
               │                  │            │                  │
  TXT文档 ──► │  文档分块         │            │  用户提问         │
               │  (按段落拆分)     │            │                  │
               │                  │            │  ┌────────────┐  │
               │  BGE 语义模型     │            │  │ 语义检索    │  │
               │  把每块转成向量   │            │  │ (向量内积)  │  │
               │                  │            │  └─────┬──────┘  │
               │  向量存入内存     │            │        │         │
               │  (NumPy 数组)     │            │  检出 Top-5 相关块│
               │                  │            │        │         │
               └─────────────────┘            │  ┌─────▼──────┐  │
                                               │  │ DeepSeek API│  │
                                               │  │ 基于知识库  │  │
                                               │  │ 生成最终答案│  │
                                               │  └────────────┘  │
                                               │                  │
                                               └─────────────────┘
```

| 阶段 | 步骤 | 技术 | 为什么选它 |
|:---|:---|:---|:---|
| **文本加载** | 读取 knowledge_base/ 下的 .txt 文件 | Python open() | 无需数据库，零配置即可用 |
| **文档分块** | 按句子/段落拆分，每块 >=100 字符 | 自定义 split_documents() | 保持语义完整，不硬切 |
| **向量化** | 把文本块转成 512 维语义向量 | BAAI/bge-small-zh-v1.5 | 中文语义检索效果最好的开源小模型 |
| **相似度计算** | 问题向量与所有块向量做内积，取 Top-5 | NumPy dot product | 无外部依赖，内存内毫秒级检索 |
| **生成答案** | 把检索到的上下文 + 问题拼成 prompt 发 DeepSeek | DeepSeek Chat API | 成本低、中文能力强 |

## 构建思路

### 为什么选 Streamlit 而不是 Flask？

- 知识库问答是典型的**数据探索型应用**，不需要复杂的路由和鉴权
- Streamlit 原生支持聊天界面（`st.chat_message` / `st.chat_input`），10 行代码实现对话 UI
- 内置 session_state 管理会话状态，不需要额外 Redis 或数据库
- 部署到 Streamlit Cloud 只需推 GitHub，零配置

### 为什么选 BGE 而不是直接用 DeepSeek 全文？

- 大模型有 token 上限，一本产品手册几万字塞不进去
- 直接用全文调 API 成本高（每次问答消耗数万 token）
- BGE 模型本地运行，检索阶段不产生任何 API 费用
- 检索后只需把 Top-5 小块发给 DeepSeek，token 消耗大幅降低

### 为什么用 NumPy 手算相似度而不用向量数据库？

- 知识库规模小（几十到几百个块），NumPy 矩阵运算完全够用
- 免去安装配置 Faiss/Milvus 的复杂度
- 代码更易读——`np.dot(query_vec, vectors.T)` 一行搞定

### RAG 与传统搜索的关键区别

| 对比维度 | 传统关键词搜索 | 本系统（RAG） |

## 常见问题

### Q1: RAG 和直接调大模型有什么区别？

直接调大模型是"凭记忆回答"，RAG 是"先查资料再回答"。如果知识库里有写"退货需要三样材料"，RAG 检索到这段话后喂给模型，答案就基于事实，而不是模型自己编。

### Q2: 为什么会选 BGE 模型？

BAAI/bge-small-zh-v1.5 是中文语义检索领域的标杆小模型（约 100MB），在 C-MTEB 中文评测榜单上排名前列。比 OpenAI text-embedding 免费、比 TF-IDF 精准、比大模型省钱。本地加载，每次检索不消耗任何 API token。

### Q3: 向量检索的相似度阈值 0.3 怎么定的？

BGE 模型的向量是 L2 归一化后的，内积等价于余弦相似度。对相关文本的内积通常在 0.4-0.9，不相关的在 0-0.2。0.3 是实践调出来的经验值——太低会引入噪音，太高可能漏掉相关内容。实测数据：

- 阈值 0.1：召回率约 95%，但平均每个问题拉回 8.6 个块（噪音多）
- 阈值 0.3：召回率约 88%，平均 3.2 块（平衡点）
- 阈值 0.5：召回率约 62%，平均 1.4 块（漏检严重）

### Q4: 知识库文档更新后需要做什么？

把新的 `.txt` 放入 `knowledge_base/` 文件夹，点"重建索引"按钮。系统会重新读取所有文档 → 分块 → 向量化，整个过程在本地完成，几秒到几十秒不等（取决于文档大小）。

### Q5: 为什么用 Streamlit 而不是 Flask？

Streamlit 专为数据应用设计，内置聊天组件、session 管理、热重载，15 行代码就能做一个问答界面。而 Flask 做对话 UI 需要手写 WebSocket + 前端框架，开发量大得多。部署也简单——推 GitHub 后 Streamlit Cloud 自动部署。

### Q6: 为什么不用向量数据库（Faiss/Milvus）？

当前知识库规模（几十到几百个文本块）用 NumPy 矩阵运算完全够用，一行 `np.dot()` 毫秒级出结果。引入 Faiss 反而增加了依赖和配置复杂度。如果未来知识库扩展到万级条目，再换用 Faiss 也很容易——接口和 NumPy 高度兼容。

### Q7: 模型下载失败怎么办？

`app.py` 第 11 行有镜像配置：
```python
# os.environ["HF_ENDPOINT"] = "https://hf-mirror.com"  # 本地开发时启用
```
取消注释即可用国内镜像下载模型，速度更快。

### Q8: Streamlit 部署到 Cloud 有什么注意事项？

- 依赖放在 `requirements.txt`，Streamlit Cloud 会自动 `pip install`
- 模型首次加载会从 HuggingFace 下载（约 100MB），冷启动需要 1-2 分钟
- 不需要 Dockerfile，Streamlit Cloud 直接用仓库里的 app.py

### Q9: 知识库里没有答案时，模型会胡说吗？

prompt 里明确写了"如果知识库中没有相关信息，请说明无法回答"。实测 DeepSeek 在无相关信息时确实会回复"抱歉，知识库中没有相关内容"。但如果知识库里有半相关的模糊段落，模型可能会过度联想——所以阈值不能设太低，避免把弱相关块喂进去。

### Q10: 你的分块策略为什么定在 100 字符？有没有更好的方案？

当前是"累积到 >=100 字符或遇到句号则切块"，属于最简单的逻辑。更好的方案：

- **滑动窗口分块**：每 100 字符一块，相邻块重叠 30 字符（避免关键信息落在边界）
- **按标题层级分块**：如果文档有 Markdown 标题，按 # 层级切（保持结构完整性）
- **语义分块**：用模型判断句子相似度，相似度骤降处切（最精准但慢）

当前方案适合纯文本说明书，如果未来文档变复杂（表格/列表/多层标题），需要升级。

### Q11: 如果两个检索块内容矛盾怎么办？

当前没有处理。比如知识库里同时有"退货期限 7 天"和"退货期限 30 天"，两个都达到阈值就会都喂给模型，模型可能随机站队。生产级的做法是：按来源文件的时效性/优先级做排序，或在 prompt 里告知模型存在矛盾让它说明。

### Q12: 向量全存内存，进程重启怎么办？

每次重启必须重建索引（重新加载文档 → 分块 → 向量化）。BGE 模型加载约 5-10 秒，向量化几百个块不到 1 秒，总共十几秒，可接受。如果要加速冷启动，可以用 `np.save('vectors.npy')` 把向量持久化到磁盘，重启时直接 `np.load`，跳过重新向量化。

### Q13: 多轮对话会丢失上下文，为什么不存历史？

当前每次问答独立：只把当前问题 + 检索到的知识库段落发 DeepSeek，不带上轮对话。理由是知识库问答是"查资料"不是"聊天"，上一轮问退货、下一轮问发货没关系。但如果要做追问（"那第二条呢？"），需要把 `st.session_state.messages` 最近 N 轮拼进 prompt。

### Q14: 如果 DeepSeek API 挂了或超时，你的降级方案是什么？

当前代码只返回报错信息，没有降级。实际应该分三层：

1. **重试**：httpx 已有 60s 超时，可以加 retry（指数退避 3 次）
2. **降级**：API 不可用时，直接返回检索到的知识库原文作为答案
3. **告警**：连续失败 N 次后 UI 上显示红色横幅提醒用户

### Q15: 你怎么衡量检索质量？有没有做评估？

目前靠人工抽查：输入 20 条已知答案的问题，检查检索到的 Top-3 是否包含正确答案所在段落。正式的 RAG 评估应该用 RAGAS 框架：

- **Context Precision**：检索到的相关内容占比
- **Context Recall**：相关文档被检索到的比例
- **Faithfulness**：生成的答案是否忠于检索到的上下文
- **Answer Relevancy**：答案是否切题

## 实现细节补充

### BGE 模型的更多细节

**为什么是 512 维？**
BAAI/bge-small-zh-v1.5 固定输出 512 维向量。维度越高表达能力越强，但计算和存储开销更大。512 维对中文短文本检索足够了——OpenAI text-embedding-3-small 也是 512 维起步。

**向量做了归一化没有？**
sentence-transformers 的 `encode()` 默认返回 L2 归一化向量，所以直接做内积（`np.dot`）等价于余弦相似度。这也是相似度值的范围在 -1 到 1 之间的原因。

**模型下载到哪里？**
`os.environ["HF_HOME"]` 设到了 `~/.cache/huggingface`。首次加载时自动下载约 100MB 的模型文件，之后直接读缓存。Streamlit Cloud 每次部署会清缓存，所以冷启动都要重新下载。

### 分块策略的边界情况

`split_documents()` 的设计有几个隐含逻辑：

1. 空行被跳过（`if not line: continue`）——这可能在表格场景下丢数据
2. 短行（<5 字符）直接追加不触发切块——保护了标题和短标签
3. 切块条件有两种：长度 >=100 或行尾是句号/感叹号/问号/冒号
4. 最小块长 20 字符：太短的块没有检索意义，直接丢弃

一个已知的边界问题：如果文档里有一段 500 字符的纯描述（没有标点断句），它会被切成一个超长块，检索时可能降低精度。

### stderr/stdout patch 的原理

`SemanticModel.load()` 里把 `sys.stdout.flush` 替换成了安全版本。原因是：

- Streamlit 启动时关闭了 stdout 的底层文件描述符
- sentence-transformers 加载模型时内部用 tqdm 显示进度条
- tqdm 每次更新会调 `sys.stdout.flush()`
- 这个调用操作已关闭的文件描述符 → `ValueError: I/O operation on closed file`

解决方案是 monkey-patch flush 方法，吞掉这个异常。这是 Streamlit + transformers 组合的经典坑。

### Streamlit Cloud 部署的特殊之处

**不需要 Dockerfile**。Streamlit Cloud 的工作方式：

1. 连接 GitHub 仓库
2. 自动检测 `requirements.txt` 并安装依赖
3. 从仓库根目录运行 `streamlit run app.py`
4. 默认端口由平台分配，不需要手动设 `--server.port`

**注意事项**：
- 平台分配的磁盘空间有限（约 1GB），模型占用约 100MB
- 首次部署模型下载可能需要 2-3 分钟（取决于 HuggingFace CDN）
- 没有持久存储——知识库文件必须跟着代码仓库一起推送
